# Implementation Plan: Remote Movie Library Overview

**Branch**: `001-remote-movie-catalog` | **Date**: 2026-09-16 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-remote-movie-catalog/spec.md`

## Summary

A Rust CLI tool exports the movie library from a home Jellyfin server via its REST API (title,
release year, genre, thumbnail) and generates a self-contained static site — an HTML page with
vanilla JavaScript, the exported catalog data, and local thumbnail image files — that can be
hosted anywhere reachable from the internet. Once published, the site needs no connection to
the Jellyfin server or home network and makes no runtime calls back to any dynamic backend, so
it satisfies "browsable and searchable from anywhere without VPN" while keeping the media
server itself unreachable from the internet. Scheduling repeated runs of the tool and
publishing/hosting its output are explicitly out of scope for the tool itself, per the user's
technical approach — both are the responsibility of whatever invokes it.

## Technical Context

**Language/Version**: Rust (stable toolchain, 2021 edition)

**Primary Dependencies**: `reqwest` (blocking HTTP client) for the Jellyfin REST API, `serde` /
`serde_json` for (de)serialization, `clap` (derive) for CLI argument parsing, `log` + `env_logger`
for structured stderr logging. No async runtime (`tokio`), no HTML templating engine, no web
framework — the CLI is a one-shot batch job, and the HTML output is generated by substituting a
data marker into a static template string, per Principle II (Simplicity & YAGNI).

**Storage**: N/A (stateless per run) — reads from the Jellyfin REST API, writes plain files
(HTML, JS, JSON, image files) to a local output directory. No database.

**Testing**: `cargo test`, with `wiremock` used to stub Jellyfin API HTTP responses so contract
and integration tests run without a live Jellyfin server (Principle I: Test-First).

**Target Platform**: Linux (the tool is expected to run on or near the home network, e.g. on the
same host as Jellyfin or another always-on home machine); Rust's portability means macOS/Windows
are not actively excluded but are not a target for this feature.

**Project Type**: Single project — a standalone Rust CLI binary. There is no separate
frontend/backend split: the "frontend" is static output the CLI generates, not a running service.

**Performance Goals**: A full export-and-generate run completes in well under 2 minutes for a
library of several thousand movies (aligned with spec SC-004's "several thousand titles" scale),
so the tool is cheap enough to run repeatedly on a schedule.

**Constraints**:
- The generated site MUST make no runtime network requests to the Jellyfin server or to any
  dynamic backend (FR-006); loading static assets — the page's own JS/CSS/images from wherever
  it is hosted — is not a "connection to the media server" and is permitted.
- The movie catalog data (titles/years/genres) MUST be embedded directly in the generated HTML
  (inline `<script>` data block), not fetched at runtime, so the page is fully usable from a
  single loaded document.
- Jellyfin credentials (API key) MUST NOT appear anywhere in the generated output directory.
- A failed or partial run MUST NOT corrupt or replace a previously generated good output (FR-009
  — external hosting must be able to keep serving the last good snapshot).

**Scale/Scope**: Single Jellyfin library type (movies) for v1; up to several thousand movie
entries (spec SC-004).

- **I. Test-First (NON-NEGOTIABLE)** — PASS. Testing strategy mandates tests before
  implementation: fixture-based parsing tests for Jellyfin API responses, unit tests for

  export→generate pipeline — all runnable via `cargo test` without a live Jellyfin instance.
- **II. Simplicity & YAGNI** — PASS. Single binary, blocking HTTP client (no async runtime for a
  one-shot batch job), no templating engine (plain string substitution into a static template),
  no built-in scheduler/service/publishing logic — those are explicitly left to the invoking

  CLI flag contract and the embedded catalog JSON schema (`contracts/`) are the tool's public
  interfaces, and changes to either follow the constitution's MAJOR/MINOR/PATCH policy.

```text
    └── assets/

        └── styles.css             # (optional) static stylesheet, copied as-is

tests/
├── contract/                 # Jellyfin API response parsing against fixture JSON
├── integration/                # wiremock-backed: run pipeline end-to-end, assert output files
└── unit/                        # pure logic: filtering/mapping, template substitution
```

**Structure Decision**: Option 1 (single project) — a standalone Rust binary crate. This matches
the user-specified "CLI tool only" scope: there is no separate hosted service, so no
frontend/backend or mobile+API split applies. The "frontend" the CLI produces is static output
artifacts (HTML/JS/data/images), not a service this codebase runs.
